# OAuth and account

MultiAI CLI signs in as a public native OAuth client: it has a `client_id`, but no client
secret. Browser login uses Authorization Code with PKCE (a one-time proof generated by
the client), while device login is available when a loopback browser callback is not
practical.

## Configure the application in multiai.store

Create one OAuth application in `multiai.store` with these exact values:

| Setting | Value |
| --- | --- |
| Name | `MultiAI CLI` |
| Application type | On device — IDE, CLI, or application |
| Redirect URI | `http://127.0.0.1:1/oauth/callback` |
| Permissions | Sign-in, profile, email, balance and limits, API key list, model access |
| Device authorization | Enabled |
| Client secret | Do not create or use one |

Register only the IPv4 loopback address shown above. Do not add `localhost` or an IPv6
callback. At runtime the CLI listens on a dynamic `127.0.0.1` port; the registered
port-`1` URI identifies the native loopback callback pattern expected by MultiAI.

After creating the application, copy its public `client_id`. Production builds embed that
value. Development and staging builds can override it:

```sh
MULTIAI_OAUTH_CLIENT_ID=YOUR_PUBLIC_CLIENT_ID multiai login
```

The default issuer is `https://multiai.store`; `MULTIAI_OAUTH_ISSUER` is intended only
for controlled development or staging environments.

## Sign in and inspect the account

Browser login is the default. The CLI starts a temporary loopback listener, opens the
authorization page, validates the callback, and closes the listener:

```sh
multiai login
```

If the callback cannot reach the terminal, use the device flow and approve the displayed
code in a browser:

```sh
multiai login --device
```

Both flows request `openid profile email account:read keys:read ai:invoke`. In the TUI,
the equivalent commands are `/login`, `/login --device`, and `/login --session-only`.
Web and VS Code expose the same browser, device, and session-only choices.

Show the current profile, wallet, subscription limits, granted scopes, connection
expiration, and masked API keys with:

```sh
multiai account
multiai account --json
```

Use `/account` for the same account view in the TUI. `/usage` remains the local session
token and context-window report; it does not report the MultiAI wallet.

## Identity and profile changes

The stable account identity is the OpenID Connect pair `(iss, sub)` (issuer and subject).
Email, display name, avatar, and Telegram are profile attributes, not identifiers.

MultiAI CLI refreshes `/oauth/userinfo` after login and after every token refresh.
Account panels load wallet, limits, connection data, and masked keys from
`/api/oauth/v1/snapshot`. Changing email, name, avatar, or Telegram therefore keeps the
session signed in and updates the displayed profile on the next refresh. The CLI does
not store Telegram. If the server assigns a different `sub`, the CLI treats it as a
different account.

## Token storage and session-only mode

The refresh token is stored in Windows Credential Manager, macOS Keychain, or Linux
Secret Service through the system keyring. Access tokens, ID token claims, profiles, and
account snapshots stay in process memory. MultiAI CLI never writes an OAuth token to a
plaintext file.

If the keyring is unavailable, interactive clients can offer a process-only session. For
a non-interactive terminal, opt in explicitly:

```sh
multiai login --session-only
multiai login --device --session-only
```

This session ends when the process exits. On first launch, MultiAI CLI removes only the
recognized legacy credential file `~/.kimi-code/credentials/kimi-code.json`; it ignores
the rest of `~/.kimi-code`.

## Expiration, revocation, and account state

Access-token expiration is normally invisible: one synchronized refresh runs and the
failed request is retried once. Refresh tokens expire after 30 days of inactivity or 90
days of total life, after which a new interactive login is required.

The following conditions clear the local session, remove `managed:multiai` models, and
return the client to the ordinary signed-out state:

- the account is deleted, blocked, or otherwise unavailable;
- the connection is revoked, the password is reset, or MFA is disabled;
- the OAuth client is archived;
- token rotation is ambiguous, returns `invalid_grant`, or cannot be committed safely;
- a refreshed identity token fails signature or claim validation.

Logout first attempts to revoke the refresh token, then always clears the local session
and managed configuration even when the issuer is unavailable:

```sh
multiai logout
```

## Balance, scopes, and rate limits

An HTTP `402 insufficient_quota` response means the MultiAI balance is exhausted. The
client keeps the account signed in, does not refresh the token, and directs the user to
`https://multiai.store/account` to add funds.

An `insufficient_scope` response also keeps the session. Update the OAuth application's
permissions in `multiai.store`; repeated sign-in cannot grant a permission the
application itself does not request. For HTTP `429`, the client respects `Retry-After`
and does not convert a rate limit into logout.

## Security checks

MultiAI CLI loads OAuth metadata before authorization and rejects authorization, token,
device, revocation, user-info, or JWKS endpoints on another origin. ID tokens must use
RS256 and pass `kid`, JWKS signature, `iss`, `aud`, `exp`, `iat`, `nonce`, and claim-type
checks with a 60-second clock skew.

Callback URLs, authorization codes, PKCE verifiers, device and user codes, and values
beginning with `ma-oauth-` are redacted from diagnostic logs.

## Models after login

After authentication, MultiAI CLI loads `/v1/models` and creates aliases named
`multiai/<model-id>`. The catalog may omit context length or other capabilities; missing
values remain unknown instead of being guessed. Requests for these aliases use the
OpenAI-compatible `/v1/responses` endpoint.
