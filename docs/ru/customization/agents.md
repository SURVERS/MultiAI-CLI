# Агенты и субагенты

Каждым сеансом MultiAI CLI управляет **основной агент**. Он понимает намерение пользователя, планирует шаги, вызывает инструменты и при необходимости поручает **субагентам** более узкие подзадачи: например, изучить незнакомую кодовую базу, параллельно проверить несколько реализаций или спланировать крупный рефакторинг, не занимая основной контекст.

Субагент получает от основного агента описание задачи, работает в собственном изолированном контексте и возвращает выводы. Он не общается с пользователем напрямую, а его промежуточные рассуждения и записи вызовов инструментов не смешиваются с историей основного агента.

## Встроенные субагенты

MultiAI CLI включает три готовых субагента, каждый для своего типа задач:

- **`coder`**: субагент по умолчанию — универсальный помощник по разработке, который может читать и записывать файлы, выполнять команды, искать код и вносить конкретные изменения.
- **`explore`**: предназначен для изучения кодовой базы; выполняет только операции чтения и не изменяет файлы. Подходит для быстрого поиска, чтения и составления сводки по репозиторию без изменения файлов.
- **`plan`**: предназначен для планирования реализации и проектирования архитектуры; ему недоступны даже команды оболочки, поэтому внимание остаётся на вопросе «как это сделать», а не на выполнении изменений.

Субагент `coder` использует почти тот же набор инструментов, что и основной агент: он может запускать команды оболочки в фоне, вести списки задач, переходить в Plan mode, вызывать Agent Skills и запускать собственных вложенных субагентов, если задача естественно делится на части. Если его ход заканчивается, пока фоновые задачи ещё выполняются, завершение будет зарегистрировано только после их окончания, поэтому родитель получит результат уже после фактического завершения всей работы.

## Как вызвать субагента

Основной агент сам планирует запуск субагентов: с учётом сложности задачи, расхода контекста и независимости подзадач он вызывает их в подходящий момент без явного указания пользователя.

Каждый запуск показывается в терминале как запрос подтверждения, если только он не соответствует разрешающему правилу или не включён YOLO mode. Так вы можете проверить описание задачи. Можно и прямо попросить основной агент использовать определённого субагента, например: «Перед изменениями используй explore, чтобы найти все нужные файлы».

Субагенты могут работать в фоне: после завершения результаты автоматически возвращаются основному агенту, без ручного опроса состояния. Также можно повторно вызвать существующий экземпляр субагента, чтобы продолжить ту же задачу.

## Изоляция контекста и расход ресурсов

Каждый субагент имеет полностью независимое окно контекста. Он видит только описание задачи, явно переданное основным агентом, и не видит историю диалога основного агента. Промежуточные рассуждения и записи вызовов инструментов субагента не возвращаются — в контекст основного агента попадает только итоговый результат.

Такая изоляция даёт два преимущества:

- **Контекст основного агента остаётся компактным** и не заполняется большими объёмами журналов исследования во время долгих сеансов.
- **Несколько субагентов могут работать параллельно**, не мешая друг другу.

Каждый субагент независимо расходует токены модели. Для простых задач запускать субагента незачем: основной агент выполнит их экономнее.

## Наследование разрешений

Субагенты наследуют правила разрешений основного агента: правила «всегда разрешать», принятые основным агентом через `/permission` или диалог подтверждения, автоматически распространяются на всех запущенных им субагентов. Поэтому им не приходится повторно подтверждать вызовы инструментов того же типа. Сам инструмент `Agent` разрешён по умолчанию, и основной агент может делегировать задачи многократно, не отвлекая пользователя.

Чтобы определённый тип инструмента был постоянно недоступен субагентам, ужесточите соответствующее правило разрешений основного агента.

## Пользовательские агенты

Помимо трёх встроенных субагентов, можно определять собственных агентов в файлах Markdown. Каждый файл описывает одного агента: frontmatter (метаданные YAML в начале файла) задаёт имя, описание и доступ к инструментам, а тело файла служит системным запросом. Пользовательским агентам можно делегировать задачи как субагентам — основной агент автоматически обнаруживает их вместе со встроенными — либо выбрать такого агента основным при запуске.

### Расположение агентов

MultiAI CLI обнаруживает файлы агентов по областям; более конкретная область имеет больший приоритет: **Явно указанный (`--agent-file`) > Проект > Дополнительные каталоги > Пользователь > Встроенные**. Если два файла определяют одинаковое `name`, побеждает область с более высоким приоритетом. В каждом каталоге рекурсивно сканируются файлы `.md`.

**Уровень пользователя** (для всех проектов):
- `$MULTIAI_HOME/agents/` (по умолчанию `~/.multiai/agents/`)
- `~/.agents/agents/`

Пользовательский каталог агентов MultiAI перемещается вместе с `MULTIAI_HOME`, а универсальный каталог `~/.agents/agents/` остаётся в настоящем домашнем каталоге ОС и может совместно использоваться разными инструментами.

**Уровень проекта** (корень проекта — ближайший вышестоящий каталог с `.git`, поиск начинается из рабочего каталога):
- `.multiai/agents/`
- `.agents/agents/`

**Дополнительные каталоги**: задаются через `extra_agent_dirs` на верхнем уровне `config.toml`:

```toml
extra_agent_dirs = ["~/team-agents", ".agents/team-agents"]
```

**Встроенные агенты** поставляются с CLI и имеют самый низкий приоритет. Обнаруженный в каталоге файл не переопределяет одноимённого встроенного агента, если в его frontmatter нет `override: true`. Файл, загруженный через `--agent-file`, считается явным намерением запуска, может переопределить одноимённого встроенного агента, превосходит все области каталогов и действует только при текущем запуске. Отдельно `$MULTIAI_HOME/SYSTEM.md` постоянно переопределяет системный запрос основного агента по умолчанию (он не участвует в обнаружении файлов агентов); взаимодействие приоритетов описано ниже в разделе о SYSTEM.md.

::: warning Модель доверия
Файлы агентов — это конфигурация запросов, а файлы уровня проекта поступают из самого репозитория, в том числе только что клонированного и ещё не заслуживающего доверия. Проектный файл может полностью подменить встроенного агента: `agent.md` с `override: true` заменяет **весь системный запрос основного агента по умолчанию**, а `coder.md` с `override: true` — тип субагента по умолчанию. В отличие от содержимого `AGENTS.md`, которое внедряется в запрос как справочные данные, переопределяющий файл *сам является* системным запросом, а файл без списка `tools` сохраняет все инструменты. Перед запуском MultiAI CLI в незнакомом репозитории проверяйте `.multiai/agents/` и `.agents/agents/` так же внимательно, как скрипты.
:::

### Формат файла агента

Файл агента — обычный Markdown с блоком frontmatter:

```markdown
---
name: reviewer
description: Strict code reviewer that reports severity-ranked findings
whenToUse: Code reviews and PR checks
override: false
model_preference: primary
tools:
  - Read
  - Grep
  - Glob
  - mcp__github__*
disallowedTools:
  - Bash
---

You are a strict code reviewer. Read the diff, then report findings grouped by severity…
```

| Поле | Обязательно | Описание |
| --- | --- | --- |
| `name` | нет | Уникальный идентификатор в kebab-case. По умолчанию используется имя файла без расширения (`review.md` → `review`); файл, у которого итоговое имя отсутствует или не соответствует kebab-case, пропускается с предупреждением |
| `description` | да | Назначение агента. Показывается основному агенту при выборе субагента, поэтому формулировка должна помогать принять решение о делегировании |
| `whenToUse` | нет | Дополнительная подсказка о том, когда следует использовать агента |
| `override` | нет | Разрешено ли файлу заменять одноимённого встроенного агента. По умолчанию `false`; `--agent-file` уже выражает явное намерение и не требует этого поля |
| `model_preference` | нет | Символическое значение по умолчанию при запуске профиля через `Agent` или `AgentSwarm`: `primary` выбирает основную модель вызывающего агента, а `secondary` — модель `[secondary_model]`. Явный параметр `model` вызова инструмента имеет приоритет; если нет ни его, ни этой настройки, по умолчанию остаётся настроенная вторичная модель. Если вторичная модель не настроена, субагент наследует модель вызывающего агента |
| `tools` | нет | Список разрешённых имён инструментов, например `Read` или `Bash`; инструменты MCP сопоставляются с шаблонами вроде `mcp__github__*`. Принимает список YAML или строку через запятую (`tools: Read, Grep`). Если поле отсутствует, разрешены все инструменты; одиночный `*` также разрешает все; пустой список (`tools: []`) отключает все инструменты |
| `disallowedTools` | нет | Список запретов с тем же синтаксисом и правилами сопоставления, применяемый после `tools` |
| `subagents` | нет | Список имён субагентов, которым этот агент может делегировать задачи, с тем же синтаксисом, что у `tools` (список YAML или строка через запятую). Если поле отсутствует, разрешены все типы; одиночный `*` также разрешает все типы |

Встроенные и пользовательские инструменты сопоставляются по точному имени с учётом регистра; записи с `mcp__` сопоставляют инструменты MCP как шаблоны. Три вида записей никогда ни с чем не совпадают и при активации профиля вызывают предупреждение: подстановочный знак вне шаблона `mcp__` (одиночный `*` в `disallowedTools` ничего не отключает), неполное имя `mcp__`, не соответствующее форме `mcp__<server>__<tool>` (`mcp__github` ни с чем не совпадает — для всего сервера используйте `mcp__github__*`), и имя, отсутствующее среди зарегистрированных и встроенных инструментов (обычно опечатка, например `read` вместо `Read`).

Тело служит системным запросом агента и при каждом построении запроса обрабатывается как шаблон: заполнители `${var}` заменяются актуальными значениями контекста; неизвестные переменные сохраняются буквально, одиночный `$` не имеет особого значения, а переменная без значения контекста превращается в пустую строку. `${base_prompt}` вставляет действующий системный запрос по умолчанию — встроенный либо переопределённый вашим `SYSTEM.md` — поэтому файл может дополнять стандартное поведение, а не заменять его. Доступные переменные перечислены ниже в разделе о SYSTEM.md.

Неизвестные поля игнорируются, поэтому новые файлы остаются читаемыми в старых версиях. Поля других агентных инструментов, например `model` Claude Code или `mode` OpenCode, также игнорируются; форма `tools` через запятую сохраняет совместимость с файлами агентов Claude Code, а при отсутствии `name` используется имя файла, что позволяет загружать файлы OpenCode. Минимального файла с `description` и телом достаточно для работы в разных инструментах.

`model_preference` применяется только к новым субагентам, когда включён эксперимент со вторичной моделью. Для `multiai web` задайте `MULTIAI_EXPERIMENTAL_SECONDARY_MODEL=1`; в экспериментальном `multiai -p` необходимый `MULTIAI_EXPERIMENTAL_FLAG=1` также включает эту возможность. Сейчас TUI игнорирует это поле. Оно никогда не задаёт конкретный псевдоним модели, а возобновлённые субагенты сохраняют прежнюю модель. Выбранное предпочтение показывается основному агенту рядом с описанием профиля, и при необходимости он всё равно может передать явный `model`.

Обнаруженный в каталоге файл с некорректным содержимым пропускается с предупреждением и не влияет на остальные файлы. Файл, явно переданный через `--agent-file`, обязан быть корректным, иначе CLI сообщит об ошибке и завершит работу.

::: warning Примечание
`tools` и `disallowedTools` определяют инструменты, показываемые модели, и повторно проверяются перед выполнением. `subagents` работает аналогично: инструмент `Agent` показывает только разрешённые вызывающему агенту типы субагентов, а `Agent` и `AgentSwarm` повторно проверяют список перед запуском; возобновление существующего субагента является исключением. Правила разрешений остаются отдельным механизмом контроля операций, требующих подтверждения.
:::

Пользовательские агенты, которым делегировали задачу как субагентам, работают без встроенной инструкции субагента («последнее сообщение — вся передача результата»). Если агент предназначен для делегирования, явно укажите в теле, что его последнее сообщение должно быть полным самостоятельным результатом для вызывающего агента.

### Выбор основного агента

Основной агент сеанса выбирается двумя флагами CLI. **Сейчас оба доступны только в `multiai -p` с `MULTIAI_EXPERIMENTAL_FLAG=1`**; интерактивный TUI пока отклоняет их с понятной ошибкой:

- **`--agent <name>`**: начать сеанс с указанным агентом в роли основного. Имя может относиться к встроенному агенту или любому обнаруженному файлу; неизвестное имя вызывает ошибку со списком доступных агентов.
- **`--agent-file <path>`**: загрузить один файл агента с наивысшим приоритетом для текущего запуска и начать работу с ним. Флаг принимает ровно один файл: его нельзя повторять или сочетать с `--agent`.

Пример в режиме печати:

```sh
MULTIAI_EXPERIMENTAL_FLAG=1 multiai -p --agent reviewer "Review the changes on this branch"
```

Привязанный агент становится идентификатором сеанса: он закрепляется при первой привязке и впоследствии не может быть изменён. Повторный выбор уже привязанного агента, например при возобновлении с тем же `--agent`, ничего не делает; выбор другого завершается ошибкой «already bound».

При настройке основного агента используйте в теле `${base_prompt}`, чтобы сохранить внедрение окружения, инструкций рабочей области и Skill из стандартного запроса. Тело без `${base_prompt}` полностью владеет запросом, что подходит для самостоятельных субагентов.

### Переопределение системного запроса основного агента через SYSTEM.md

Чтобы постоянно переопределить системный запрос основного агента без передачи `--agent` или `--agent-file` при каждом запуске, создайте `$MULTIAI_HOME/SYSTEM.md` (по умолчанию `~/.multiai/SYSTEM.md`; он перемещается вместе с `MULTIAI_HOME`). Пока файл существует и не пуст, он полностью заменяет встроенный системный запрос основного агента по умолчанию — и только запрос: описание и набор инструментов наследуются из встроенных значений. Сейчас SYSTEM.md действует только в `multiai web` и `multiai -p` с `MULTIAI_EXPERIMENTAL_FLAG=1`; интерактивный TUI его игнорирует.

SYSTEM.md содержит обычное тело Markdown: frontmatter не нужен и не читается. Отсутствующий или пустой файл не влияет на работу, а при ошибке чтения с предупреждением используется встроенный запрос. Явное намерение по-прежнему приоритетнее: проектный одноимённый файл агента с `override: true` и любой файл из `--agent-file` имеют больший приоритет, а выбор другого агента через `--agent` полностью обходит SYSTEM.md. Внутри пользовательской области SYSTEM.md превосходит одноимённый файл, обнаруженный в каталогах `agents/`.

Как и тело обычного файла агента, SYSTEM.md при каждом построении запроса обрабатывается как шаблон: заполнители `${var}` в теле заменяются значениями актуального контекста:

| Переменная | Содержимое |
| --- | --- |
| `${skills}` | Объединённое внедрение Agent Skills; пусто, если инструмент `Skill` недоступен |
| `${agents_md}` | Содержимое файлов инструкций рабочей области, например `AGENTS.md` |
| `${cwd}` | Текущий рабочий каталог |
| `${cwd_listing}` | Список содержимого рабочего каталога |
| `${os}` | Тип операционной системы |
| `${shell}` | Имя и путь оболочки, например `bash (\`/bin/bash\`)` |
| `${now}` | Текущее время в формате ISO |
| `${additional_dirs_info}` | Дополнительные каталоги, добавленные в рабочую область; пусто, если их нет |
| `${base_prompt}` | Системный запрос по умолчанию. В самом `SYSTEM.md` это встроенное значение; в файле агента — действующее значение: встроенное или переопределённое вашим `SYSTEM.md` |

Неизвестные переменные сохраняются буквально, одиночный `$` не имеет особого значения, а переменная без значения контекста превращается в пустую строку. Три готовых блока — `${windows_notes}`, `${additional_dirs_section}` и `${skills_section}` — выводят соответствующий раздел встроенного запроса либо пустую строку, если он неприменим. Этих переменных достаточно, чтобы воссоздать каркас встроенного запроса, например:

```markdown
You are MultiAI, running at ${cwd} on ${os}.

${agents_md}

${skills}
```

## Файлы инструкций

Глобальные инструкции специально для MultiAI можно хранить в `$MULTIAI_HOME/AGENTS.md` (по умолчанию `~/.multiai/AGENTS.md`). При переносе корня данных через `MULTIAI_HOME` этот глобальный файл инструкций перемещается вместе с ним. Универсальные инструкции для разных инструментов по-прежнему можно хранить в `~/.agents/AGENTS.md` в настоящем домашнем каталоге ОС, а проектные инструкции остаются в дереве проекта, например `.multiai/AGENTS.md` или `AGENTS.md`.

## Хранение данных в каталоге сеанса

Состояние выполнения субагентов сохраняется в подкаталоге `agents/` текущего каталога сеанса. Каждый экземпляр субагента имеет собственный каталог с файлом `wire.jsonl`, который в хронологическом порядке записывает запросы, историю сообщений и итоговое состояние. Фоновые субагенты также публикуют состояние жизненного цикла через подкаталог `tasks/`.

::: warning Примечание
Каталоги сеансов, wire-файлы и записи задач — локальные отладочные материалы, которые могут содержать запросы пользователей, вывод команд, пути репозитория, результаты инструментов или следы учётных данных. Не публикуйте эти файлы напрямую в открытых репозиториях, задачах или журналах чатов; перед передачей удаляйте конфиденциальные сведения.
:::
